# Roadmap: VDR Agent Service

## Overview

`vdr-agent` is a new FastAPI microservice that transforms the ESG VDR platform from passive document storage into an active intelligence layer. The build starts with a correctly-engineered service scaffold and database foundation — including the concurrency-safe `FOR UPDATE SKIP LOCKED` document claiming pattern that cannot be safely retrofitted later — then layers in the AI generation pipeline (parallel section summaries, per-topic fitment evaluations via AWS Bedrock), the REST API surface consumed by `vdr-frontend`, and finally wires the existing frontend to surface real AI results in place of the current hardcoded ESG scope list and empty data columns.

**Depends on**: Nothing (first phase)
**Requirements**: None (foundation infrastructure)
**Success Criteria** (what must be TRUE):

  4. pyproject.toml declares all dependencies with pinned versions matching ingestion-service conventions (Poetry, psycopg 3.3.3, FastAPI 0.115+, boto3)

### Phase 2: DB Schema
**Goal**: The four vdr_agent tables exist in PostgreSQL with correct columns, constraints, indexes, and a stale-lock recovery column — everything the polling loop and generation pipeline will write to
**Depends on**: Phase 1
**Requirements**: PROC-01, PROC-04
**Success Criteria** (what must be TRUE):
  1. Running migrations creates `vdr_agent.topics`, `vdr_agent.processing_state`, `vdr_agent.document_summaries`, and `vdr_agent.fitment_results` tables
  2. `processing_state` has `summary_status` with values `pending | processing | done | failed` and a `processing_started_at` timestamp for stale-lock detection
  3. A partial index on `(summary_status, created_at) WHERE summary_status IN ('pending', 'failed')` exists on `processing_state`
  4. `fitment_results` has a UNIQUE constraint on `(document_id, topic_id)` enabling `ON CONFLICT DO UPDATE` for safe re-runs
  5. Migration script is idempotent (can be run twice without error)

### Phase 3: DB Layer
**Goal**: All database access is centralised in async DAOs that use a shared AsyncConnectionPool — no direct connection management scattered across the codebase
**Depends on**: Phase 2
**Requirements**: None (infrastructure layer consumed by PROC-01 through PROC-04 and API-01 through API-03)
**Success Criteria** (what must be TRUE):
  1. `DatabasePool` singleton initialises an `AsyncConnectionPool` on startup and closes it cleanly on shutdown
  2. `TopicDAO` supports insert, list-by-project, update, and delete operations using raw SQL and `async with pool.connection()` scoping
  3. `ProcessingStateDAO` supports poll-claim query (FOR UPDATE SKIP LOCKED), status update, and stale-lock recovery query
  4. `DocumentSummaryDAO` and `FitmentResultDAO` support upsert operations that do not hold a DB connection during Bedrock calls
  5. All DAO methods are async and use `psycopg` 3 `AsyncConnection` — no sync psycopg2 calls exist anywhere

### Phase 4: LLM Client
**Goal**: A single boto3 Bedrock wrapper handles all Claude API calls from an executor thread, with a semaphore-bounded rate limiter that prevents Bedrock quota exhaustion
**Depends on**: Phase 1
**Requirements**: None (infrastructure layer consumed by PROC-02 and PROC-03)
**Success Criteria** (what must be TRUE):
  1. `ClaudeClient.invoke(prompt)` executes `boto3.client.invoke_model()` inside `asyncio.to_thread()` and returns the response without blocking the event loop
  2. `GlobalRateLimiter` limits concurrent Bedrock calls to a configurable maximum (default 10); additional callers await the semaphore
  3. The semaphore is lazily initialised inside a running event loop (not at module import time)
  4. A `ThreadPoolExecutor` with sufficient workers (≥ 50) is configured so concurrent `asyncio.to_thread()` calls do not deadlock
  5. Claude response truncation is detected by checking `stop_reason`; truncated responses are logged as warnings
**Plans**: 2 plans
- [ ] 04-01-PLAN.md — LLM client: async invoke() function, ClaudeClientError, GlobalRateLimiter singleton
- [ ] 04-02-PLAN.md — Config fields + ThreadPoolExecutor wiring in startup

### Phase 5: Polling Loop
**Goal**: The service autonomously detects documents that have completed embeddings but no AI summary, atomically claims them one at a time, and hands them off to the processor — with no duplicate processing possible
**Depends on**: Phase 3, Phase 4
**Requirements**: PROC-01
**Success Criteria** (what must be TRUE):
  1. The poller runs as a background asyncio task started in the FastAPI lifespan and cancelled cleanly on shutdown (task reference is stored; done callback logs completion)
  2. The poller queries `ai_rag.*` for documents where `status = 'completed'` and claims them with `FOR UPDATE SKIP LOCKED` — no plain `SELECT` then `UPDATE` pattern exists
  3. Two running vdr-agent instances do not process the same document (enforced by SKIP LOCKED at the DB level)
  4. Stale `processing` rows older than a configurable threshold (default 30 min) are detected and reset to `pending` on each poll cycle
  5. Poll batch size is bounded by a configurable `LIMIT` (default 5); poll interval is configurable (default 10 s)
**Plans**: 2 plans
- [ ] 05-01-PLAN.md — Config fields (poll_interval_seconds, poll_batch_size, stale_lock_threshold_minutes) + ProcessingStateDAO.find_unregistered_documents()
- [ ] 05-02-PLAN.md — app/worker/ package (poller.py, processor.py stub) + startup.py lifespan wiring

### Phase 6: AI Summary Generation
**Goal**: Every claimed document gets an AI summary: section chunks are summarised in parallel via Claude, then collapsed into a single combined document summary stored in the DB
**Depends on**: Phase 5
**Requirements**: PROC-02
**Success Criteria** (what must be TRUE):
  1. After a document is claimed, all its embedding chunks are fetched from `ai_rag.*` and partitioned into sections
  2. Section summaries are generated in parallel (up to GlobalRateLimiter concurrency limit) and all results are collected before proceeding
  3. A second Claude call combines the section summaries into a final document summary
  4. The final summary is written to `vdr_agent.document_summaries` and `summary_status` is set to `done`
  5. If any Claude call fails, `summary_status` is set to `failed` and processing stops for that document (no retry)
**Plans**: 2 plans
Plans:

- [ ] 10-02-PLAN.md — Component wiring: ScopeSidebar API-driven topics, ScopeDetails status + fitment columns + polling

### Phase 7: Fitment Generation
**Goal**: Every document with a completed summary gets a fitment evaluation for each active ESG topic, written to the DB — completing the core product value
**Depends on**: Phase 6
**Requirements**: PROC-03
**Success Criteria** (what must be TRUE):
  1. All active topics for the document's project are fetched at the start of fitment generation
  2. Fitment evaluations for all topics are fired in parallel (bounded by GlobalRateLimiter) and all results are collected
  3. Each fitment result is upserted into `vdr_agent.fitment_results` using `ON CONFLICT DO UPDATE` (safe for re-runs)
  4. Individual topic fitment failures are recorded as `failed` status for that row; other topics continue processing
  5. When all topics are processed, `vdr_agent.processing_state` is updated to `done` with a completion timestamp

### Phase 8: Topic CRUD API
**Goal**: ESG topics can be created, listed, updated, and deleted via REST endpoints — enabling the frontend to replace its 19 hardcoded scope names with project-specific topics
**Depends on**: Phase 3
**Requirements**: TOPIC-01, TOPIC-02, TOPIC-03, TOPIC-04
**Success Criteria** (what must be TRUE):
  1. `POST /vdr-agent/topics` creates a topic with name and instruction text, returning the created topic with its ID
  2. `GET /vdr-agent/topics?project_id=<id>` returns all topics for a project as a JSON array
  3. `PATCH /vdr-agent/topics/{id}` updates a topic's name and/or instruction text and returns the updated topic
  4. `DELETE /vdr-agent/topics/{id}` removes a topic and returns HTTP 204
  5. All endpoints return appropriate HTTP error codes for not-found and invalid input cases

### Phase 9: Results API
**Goal**: Consumers can query the AI summary and fitment results for any document, and list all documents for a project with their current processing status
**Depends on**: Phase 7, Phase 8
**Requirements**: API-01, API-02, API-03
**Success Criteria** (what must be TRUE):
  1. `GET /vdr-agent/documents/{id}/summary` returns the AI-generated summary text and its status (`pending | processing | done | failed`)
  2. `GET /vdr-agent/documents/{id}/fitment` returns an array of fitment results — one per active topic — each with topic name, result text, and status
  3. `GET /vdr-agent/documents?project_id=<id>` returns all documents for the project with their `summary_status` and overall `processing_status` fields included
  4. Endpoints return HTTP 404 for unknown document or project IDs
  5. A document with status `pending` or `processing` returns its current status (not an error) so the frontend can show a loading state
